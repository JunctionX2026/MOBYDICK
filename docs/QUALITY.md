# 품질 계약

품질 검증은 변경에 가장 가까운 빠른 신호부터 시작하고, 푸시 전에 전체 회귀로 넓혀요. 테스트 수가 아니라 사용자가 겪을 위험을 줄이는지를 기준으로 유지해요.

## 검증 계층

| 시점    | 명령                              | 보호하는 계약                          |
| ------- | --------------------------------- | -------------------------------------- |
| 구현 중 | 변경한 워크스페이스의 단위 테스트 | 계산, 상태 전이, 입력 경계             |
| 푸시 전 | `pnpm verify`                     | 정적 검사, 타입, 단위 테스트           |
| PR      | CI                                | 커밋 형식, 정적 검사, 타입, 단위 테스트 |

## 반드시 테스트하는 것

- **접합부 스키마.** `Suggestion`, `Workflow`, `OperationSpec`은 형식이 깨지면 파이프 전체가 조용히 망가져요.
- **지역코드 정규화.** 같은 지역의 다른 표기가 같은 코드로 모이는지, 매칭되지 않은 값이 사유와 함께 남는지 확인해요.
- **조인 결과 판정.** 행 수 급감, 매칭률 급락, 타입·단위 충돌, 결측률 급증이 실제로 정지 신호를 만드는지 확인해요.
- **배포 계약.** 배포된 엔드포인트가 캔버스 결과와 같은 값을 돌려주는지, 파라미터가 의도한 범위만 바꾸는지 확인해요.
- **입력 경계.** 외부 응답을 검증 없이 도메인 타입으로 통과시키지 않는지 확인해요.

## 테스트하지 않는 것

- 단순 렌더링, CSS 클래스 목록, 애니메이션 이름
- 프레임워크 기본 동작
- 같은 공용 컴포넌트를 여러 화면에서 반복 확인하는 검사
- LLM 응답의 문장 내용. 형식과 스키마만 검증하고 문장 품질은 사람이 판단해요.

## 삭제 기준

삭제한 테스트가 지키던 위험이 다른 계층에 없다면 먼저 대체 계약을 만든 뒤 삭제해요. 사용자 결과와 직접 연결되지 않는 검사는 유지하지 않아요.

## 사람이 확인하는 것

시스템이 감지할 수 없는 항목은 자동화하지 않고 데모 리허설에서 사람이 확인해요.

- 이 데이터가 질문에 맞는가
- 지역 · 기간 범위가 적절한가
- 이 결과가 쓸 만한가

화면 변경은 같은 뷰포트와 상태의 변경 전후를 비교하고, 스크린샷만으로 통과시키지 않고 실제로 조작해요.
